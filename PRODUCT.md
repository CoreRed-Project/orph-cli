# PRODUCT.md

## What is Orph?

Orph is a local harness for Raspberry Pi and other offline, resource-constrained devices.

Its purpose is to standardize common on-device workflows:

* script execution
* configuration management
* system inspection
* local telemetry
* persistent state

without requiring:

* internet access
* package managers
* external services
* cloud infrastructure
* runtime dependencies

Drop the binary.

Run it.

Work locally.

## Core Problem

Most Raspberry Pi and headless environments depend on assumptions:

* network available
* package repositories online
* dependencies installed
* paths configured correctly

When those assumptions fail, workflows become fragile.

Orph removes as many assumptions as possible.

## Product Positioning

Orph is not:

* a dashboard
* a monitoring suite
* a cloud platform
* a companion app
* a tamagotchi

Orph is:

* a local operations harness
* an offline toolkit
* a reliability layer
* a workflow standardizer

The companion is an optional personality layer.

The harness is the product.

## Design Principles

### Local-first

Everything should reinforce the idea that work happens locally.

### Reliability-first

The interface should communicate confidence and stability.

### Low-friction

Users should understand the state of the machine immediately.

### Headless-friendly

Every feature should make sense on a terminal-only device.

### Resource-conscious

Nothing should feel wasteful.

## Companion Philosophy

Zeph exists to add personality.

Zeph does not define the product.

Zeph should:

* stay lightweight
* avoid dominating workflows
* provide delight
* reinforce identity

Zeph should not:

* replace operational information
* become the primary purpose of the interface

## TUI Goals

The TUI should feel like:

* a premium local operations console
* an offline control center
* a trusted utility
* a tool built for constrained environments

The TUI should not feel like:

* a generic admin dashboard
* a DevOps SaaS panel
* a monitoring clone
* a game UI

## UI Hierarchy

Priority order:

1. System state
2. Workflow execution
3. Local telemetry
4. Script operations
5. Configuration access
6. Companion presence

The companion is part of the experience.

It is not the center of the product.

## Brand Tone

Keywords:

* local
* dependable
* offline
* lightweight
* autonomous
* self-contained
* resilient
* companionable

Avoid:

* enterprise
* cloud-native
* futuristic hacker clichés
* excessive cyberpunk
* childish toy aesthetics

The goal is trustworthy utility with personality.
